# GitHub Issue Workflow

## 규칙: 코드 수정 전 반드시 이슈를 먼저 등록한다

버그를 발견하거나 기능을 추가하기 전에, **항상 GitHub 이슈를 먼저 생성한 뒤 코드를 수정**한다.

### 이슈 등록 대상 레포

- **포크 레포**: `oh0227/cochat-for-buisness-backend`
- main/upstream 레포가 아닌 위 레포에 등록한다

### 이슈 등록 절차

1. 문제 또는 작업 내용을 파악한다
2. 기존 이슈와 연관성을 확인한다
   - 연관 있으면 → **sub-issue**로 등록 (본문에 `parent: #번호` 명시)
   - 연관 없으면 → 새 독립 이슈로 등록
3. 이슈를 생성한다 (`gh issue create --repo oh0227/cochat-for-buisness-backend ...`)
4. 이슈 번호를 확인한 뒤 코드 수정을 시작한다
5. 커밋 메시지에 `closes #번호` 또는 `refs #번호`를 포함한다 (형식은 `commit-convention.md` 참고)

### Sub-issue 작성 규칙

GitHub에 공식 sub-issue 기능이 없으므로 본문 상단에 아래 형식으로 표기한다:

```
## 관련 이슈

parent: #2 (GC 스케줄러 시작 시 langchain_pg_embedding 테이블 미존재 오류)
```

### 이슈 본문 포함 항목

- **문제 요약**: 한 줄 설명
- **에러 로그**: 실제 로그 또는 스택트레이스
- **원인 분석**: 어느 파일 몇 번째 줄, 왜 발생하는지
- **영향 범위**: 관련 파일 목록
- **해결 방안**: 적용할 접근법 (선택지가 여러 개면 후보로 나열)

### 브랜치

모든 수정은 `dev` 브랜치 기준으로 작업한다.

---

## 규칙: 이슈 종료는 배포 서버에서 사용자가 직접 확인한 후에 한다

코드를 수정하고 push했다고 해서 이슈를 바로 닫지 않는다.

### 이슈 종료 절차

1. 코드 수정 완료 후 push
2. **사용자에게 배포 서버에서 확인을 요청**한다
   - "배포 후 실제 서버에서 확인해 주시면 이슈를 닫겠습니다."
3. 사용자가 "해결됐다", "확인했다" 등 확인 응답을 주면 그때 이슈를 닫는다
   ```bash
   gh issue close <번호> --repo oh0227/cochat-for-buisness-backend --comment "배포 서버에서 정상 동작 확인 완료."
   ```
4. 사용자가 "아직 안 된다"고 하면 원인을 재분석하고 새 수정을 진행한다

### 금지 사항

- 커밋 메시지의 `closes #번호`만으로 이슈를 닫는 것에 의존하지 않는다
  (GitHub 자동 close는 PR merge 기준이므로 push만으로는 닫히지 않음)
- 코드가 로컬에서 올바르다고 판단해 임의로 이슈를 닫지 않는다
